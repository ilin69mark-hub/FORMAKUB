### 10.5. CA-T-110 — Замер чтения/записи на 2000 проектах (2026-11-09)

**Основание:** отдельное разрешение владельца на выполнение CA-T-110. Замер, не изменение поведения.

**Методика.** Временный vitest-прогон (после снятия чисел удалён) с реальным Storage Adapter: `FORMAKUB_STORAGE=sqlite`, временный `FORMAKUB_DATA_DIR`; 2000 `StoredProject` с `defaultKitchen()` (реальный `calculatePrice`), сид одной записью `updateCollection`; прогрев 5 чтений; `getProject` — 100 итераций по детерминированным id; `saveProject` — 20 последовательных сохранений поверх набора 2000 (каждое переписывает коллекцию); `readCollectionStatus` — 50 итераций. Два прогона подряд, результаты стабильны.

**Среда:** Node v25.9.0, darwin/arm64, SQLite (`node:sqlite`), один хост.

| Показатель | Прогон 1 | Прогон 2 |
|---|---|---|
| Payload коллекции `projects.json` | 9 030 001 байт (8.61 MiB) | то же |
| Размер `formakub.db` | 8.64 MiB | то же |

| `getProject`: 100 итераций, total | 2 772.54 мс | 2 781.33 мс |
| `getProject`: avg / p95 / max | **27.72 / 29.67 / 37.15 мс** | **27.81 / 28.81 / 40.82 мс** |
| `getProject`: ops/s | 36.1 | 36.0 |

| Итоговое число проектов | 2000 (cap не превышен) | 2000 |

**Наблюдения (факты замера):**
- Чтение одного проекта стоит как чтение всего массива: `getProject` ≈ raw `readCollectionStatus` — доминирует `JSON.parse` 8.61 MiB; поиск/валидация/`calculatePrice` добавляют ~0.2 мс.
- Сохранение переписывает всю коллекцию: ~73.6 мс на запись при 2000. Экстраполяция **[ВЫВОД]**: 2000 последовательных `saveProject` ≈ 147 с (не измерялось).
- `saveProject` не превышает cap 2000 (`slice(-2000)`), т.е. CA-RISK-006 (тихое вытеснение 2001-го) остаётся актуальным; замер это не меняет.

**Ограничения замера:** тёплый кэш/один процесс и хост; одинаковая конфигурация у всех 2000 записей (влияет на размер payload, но не на порядок); WAL-checkpoint и дисковая скорость не изолировались; числа — ориентир для планирования, не SLA.
