## 3. Общая модель каталогов (§3)

### 3.1. Поля общей модели

Текущий `CatalogItem` (`admin/schema.ts:101–124`, `strictObject`): `id`, `catalog`, `label`, `attrs`, `priceRefs`, `status`, `sortOrder`, `version`, `createdAt/updatedAt/updatedBy`.

| Целевое поле | Статус | Где сейчас |
|---|---|---|
| id | ЕСТЬ | `id` (строго совпадает с `src/content/*` — комментарий `schema.ts:102`) |
| code | НЕТ | нет; функцию несёт `id` |
| name | ЧАСТИЧНО | `label` |
| description | НЕТ | у `CatalogItem` нет; описания живут в `content/*` и не мигрируют |
| category | ЧАСТИЧНО | роль несёт `catalog` (16 kinds); отдельной иерархической категории нет |
| family | ЧАСТИЧНО | только у `ModulePreset` (`kitchen|wardrobe` — `schema.ts:525`); у CatalogItem family нет (используется `scope` у `PriceItem`) |
| status | ЕСТЬ | см. §3.2 |
| manufacturer / model / article | НЕТ | отсутствуют полностью; то же — `modelId`-ссылки в `WardrobeConfig` без каталога (инвентарь §9 п.5) |
| unit | ЧАСТИЧНО | `unit` есть у `PriceItem`, отсутствует у `CatalogItem` (единица живёт на тарифе) |
| priceReference | ЕСТЬ | `priceRefs: роль → PriceItem.id` (11 ролей — `schema.ts:50–62`) |
| applicability | ЧАСТИЧНО | нет поля; частично — `scope` у PriceItem (`kitchen|wardrobe|shared`), `appliesTo` у промо, `zone` у пресета |
| createdAt/updatedAt | ЕСТЬ | есть (+ `updatedBy`) |

**Ключевой вывод §3:** целевая модель требует расширения `CatalogItem` (code, description, unit, applicability, manufacturer/model/article). Поскольку схема `strictObject`, расширение требует миграции записей — задача Этапа 1, не запрещённая §16.

**Пример «универсальной формы» (§3, запрет):** текущая реализация этому требованию уже отвечает на уровне данных — `attrs` разреженный и типизирован по kind (`CountertopAttrs`, `PlinthAttrs`, `SupportAttrs`, `LedStripAttrs`, `PsuAttrs`, `IdAttrs` — `contract.ts:46–88`), typed-проверка есть для `supportSystem`/`ledStrip` (`schema.ts:116–131`). Риск — при расширении kinds не превращать `attrs` в свалку.

### 3.2. Статусы (§3.1)

| Целевой | Текущий | Статус |
|---|---|---|
| `active` | `active` (CatalogItem, ModulePreset, PriceItem) | ЕСТЬ |
| `draft` | нет у каталожных сущностей; `draft` есть только у `PricingVersion` | **РЕШЕНО (Q3):** импорт создаёт записи в статусе `draft`; импорт не публикует автоматически; публикация — отдельная операция; CA-T-208 сохраняется (§16-Q3) |
| `archived` | `archived` (все три; удаление запрещено — `presets.ts:359`, `price-items.ts`) | ЕСТЬ |

**Принцип «статус ≠ участие в расчёте» (§3.1):** реализован у `PriceItem` (`status` ортогонален `usage: used|unused`, `schema.ts:150–154`, запрет `archived+used` — `schema.ts:161–165`). У `CatalogItem` участие в расчёте определяется фактом разрешения `priceRefs` в `data-resolver` — отдельного признака «участвует» нет, но и не требуется.

### 3.3. Единицы измерения (§3.2)

| Целевая | Статус |

Проверка единиц при связывании с тарифами: частично — нормализация единиц описана при импорте (`import.ts:156–164`), автоматической сверки «единица позиции ↔ единица тарифа ↔ норма расхода» нет.

## 7. Правила комплектации (§7) — ключевой структурный разрыв

§7 требует **отдельный централизованный слой правил** (тип изделия → условие → комплектующее → модель → количество/формула → ед. → ограничения → приоритет → статус).

**Текущее состояние (VERIFIED): нормы разнесены по трём местам — ровно то, что §7 запрещает.**

| Норма | Где живёт сейчас | Пример из кода |
|---|---|---|
| Количество петель шкафа | **код** (`wardrobe-hinges.ts` полосы) + дубль в `AdminParameter` readonly | `WARDROBE_HINGE_BANDS`, 8 полос |
| Количество петель кухни | **код** (`facadeDoorCount` >60 см) | `facade-geometry.ts:88` |
| Правило дверей шкафа в UI | **интерфейс** (подсказка) | `WardrobePanel.tsx:187` — и она расходится с кодом (инвентарь §9 п.1) |
| Опоры: спан/нагрузка/пеналы | **код** (`supports.ts:147–220`) + паспортные числа в `CatalogItem supportSystem` | `positionsForModule` |
| Клипсы/винты на опору | **каталог** (`SupportSystem.clipsPerLeg/screwsPerLeg`) | `content/supports.ts:57–59` |
| Анкеры пеналов | **код** (`Math.ceil(height/tallAnchorSpacingCm)`) + шаг в каталоге | `supports.ts:275` |
| Количество ящиков/полок/штанг | **код** (счётчики `wardrobe-components.ts`, лимиты в `KITCHEN_LIMITS/WARDROBE_LIMITS`) | `wardrobeDrawerCount` |
| LED: длина/участки/БП/заглушки | **код** (`lighting.ts:199–239`) | `computeLighting` |
| Вырезы/сборы за модуль | **код** (условия по типу модуля) | `engine.ts:787,816,817` |
| Лимиты секций/полок/ящиков | **каталог-константы** + **zod** (два источника) | `WARDROBE_LIMITS` vs `schema.ts:219–234` |

**Вывод:** слой «правила комплектации» как сущности отсутствует полностью. Его создание — основная нагрузка Этапа 3 и одновременно самое архитектурно чувствительное место: перенос норм из кода в данные = изменение расчётного контура, что §8/§16 не разрешают автоматически и требует отдельного решения (см. вопрос владельцу №1).

> **Решение владельца Q1 (подтверждено 2026-11-13):** управляемые нормы комплектации переносятся в отдельный слой данных. Формулы и алгоритмы расчётного ядра остаются в коде. Второй расчётный движок не создаётся. Изменения управляемых правил должны учитываться в версионировании и воспроизводимости расчётов. Конкретная реализация не придумывается — отражён только согласованный принцип и необходимые архитектурные зависимости; необходимость отдельного ADR зафиксирована в ТЗ (§12.5, задача T-0.6), содержание ADR не утверждается. Альтернатива «только view-описание норм» из вопроса №1 не принимается. (§16-Q1)

**Дополнительно подтверждённые нарушения принципа «одна норма — одно место» (инвентарь §9):** правило дверей шкафа существует в двух реализациях (`wardrobeFacadeField` тестовая vs `wardrobeFacadeGeometry` производственная, п.1); лимиты секций дублируются (schema max 2 vs LIMITS max 6 vs validation 1|2, п.9); `minSectionWidth` объявлен, но не читается (п.10); шаги ящиков: `KITCHEN_LIMITS.minDrawers=2` vs `SINK_RULES.maxDrawersPerSection=3` vs `WARDROBE_LIMITS.maxDrawersPerSection=5` vs schema `0–6` — четыре источника для «сколько ящиков».

## 16. Решения владельца (Q1–Q7) по противоречиям целевой модели

Требования v0.1 местами вступали в конфликт с решениями, уже зафиксированными в проекте. **Все семь вопросов подтверждены владельцем и зафиксированы ниже (2026-11-13).** Варианты и рекомендации аналитика, приведённые в вопросах, решениями владельца не являются.

### Вопрос 1. Перенос норм из кода в данные (§7 + Этап 3)

§7 запрещает хранить нормы в трёх местах, но ключевые нормы (полосы петель, алгоритм опор, расчёт LED, счётчики) — это **код расчётного ядра**. Их перенос в данные = изменение поведения расчёта, что §8 и §16 запрещают делать автоматически и что требует `calcVersion` (решение Q17/OI-069: версия меняется только при релизе, меняющем правила).

**Вопрос владельцу:** на Этапе 3 переносить ли нормы в данные (с пересчётом и версией) — или фиксировать кодовые нормы как «непереносимые», ограничившись их **описанием** в админке (view-only карточка правила со ссылкой на формулу)? Второй путь дешевле и не трогает движок, но формально не закрывает §7 («централизованы»).

**Решение владельца Q1 (подтверждено 2026-11-13):** управляемые нормы комплектации переносятся в отдельный слой данных; формулы и алгоритмы расчётного ядра остаются в коде; второй расчётный движок не создаётся; изменения управляемых правил учитываются в версионировании и воспроизводимости расчётов. Конкретная реализация не придумывается — отражён только согласованный принцип и необходимые архитектурные зависимости; необходимость отдельного ADR зафиксирована в ТЗ (§12.5, задача T-0.6), содержание ADR не утверждается. Альтернатива «только view-описание норм» из вопроса не принимается.

### Вопрос 2. «Управление ассортиментом без кода» (§1) против R-14 и множественности источников (§4.1)

Цель §1 («обычные операции с каталогами и ценами без исходного кода») противоречит:
- **R-14** (решение владельца): первичное создание `PriceItem` — только импортом из content, ручной CRUD create не вводится (`import.ts:36–40`);
- реальность §4.1: новый тип модуля — ≥7 правок кода (union-типы, zod, ADD_ORDER, нагрузки, manifest);
- контент-файлы `src/content/*` — исходный код (git).

**Вопрос владельцу:** что относится к «обычным операциям»?
- (а) только правка значений/цен/статусов/архивация **существующих** позиций (тогда §1 и §4.1 «создание новых типов модулей без правки нескольких источников» нужно переформулировать как «создание пресетов существующих типов» — пресеты уже data-driven);
- (б) также создание новых позиций каталога и пресетов через UI (тогда нужно отменить/скорректировать R-14 для CatalogItem/ModulePreset и определить, как новые типы модулей становятся data-driven — это архитектурное решение уровня Engine-контракта);
- (в) также новые типы модулей без кода (тогда §4.1 — отдельное крупное архитектурное решение, выходящее за рамки §16 «не утверждает новые алгоритмы», и требующее плана миграции union-типов в данные).

**Решение владельца Q2 (подтверждено 2026-11-13):** R-14 сохраняется; новые `PriceItem` создаются только контролируемым импортом; новые типы модулей требуют отдельного архитектурного решения; создание новых типов модулей через обычные операции админки не описывается как утверждённая возможность. **Не подтверждено:** объём «обычных операций» для ручного создания записей `CatalogItem`/`ModulePreset` через UI (вопрос остаётся открытым).

### Вопрос 3. Статус `draft` у каталожных позиций (§3.1) против текущей модели импорта

§3.1 вводит `draft` у сущностей каталога. Текущая draft-модель существует только у `PricingVersion` (черновик = копия опубликованного). Для каталожных позиций `draft` означает, что создание позиции и её публикация разнесены — что предполагает ручное создание (см. вопрос 2б).

**Вопрос владельцу:** нужен ли `draft` у CatalogItem/ModulePreset, если остаётся принцип «первичное создание — импортом»? (Если остаётся — `draft` не нужен, достаточно `preliminary→active`.)

**Решение владельца Q3 (подтверждено 2026-11-13):** импорт создаёт записи в статусе `draft`; импорт не публикует данные автоматически; публикация выполняется отдельной операцией; совместимость с CA-T-208 сохраняется.

### Вопрос 4. «Дата действия» тарифа (§9.1) против модели версионирования (§9.3)

§9.1 требует «дату действия» у тарифа. Текущая модель сознательно версионная (`priceVersion` + снимки), дат действия нет. Добавление дат создания временно́й цены («с 15.11 действует X») означает либо планирование публикаций, либо датированные тарифы внутри версии — оба варианта меняют контракт `PricingVersion`.

**Вопрос владельцу:** нужна ли «дата действия» как планируемое изменение цены (и тогда — планировщик публикаций), или достаточно текущей модели «публикация версии в момент изменения» (тогда поле исключить из §9.1)?

**Решение владельца Q4 (подтверждено 2026-11-13):** отдельные даты действия тарифов не вводятся; используется существующая модель `PricingVersion`. Поле «дата действия» в целевом реестре цен (§9.1) не применяется.

### Вопрос 5. Заведение категорий без данных (§5.6, §6.6, §6.7)

§6.6 и §16 прямо допускают: категории есть, модели/нормы/цены не подтверждены. §5.6 — «отсутствие цены не означает отсутствия позиции».

**Вопрос владельцу (подтверждение, не нововведение):** подтверждается ли, что на Этапе 2 допустимо завести пустые/предварительные категории и позиции со статусом `preliminary`/`unverified` и без `priceRefs`, и что диагностика трактует это как предупреждение, а не ошибку публикации? (Это влияет на правило §15.5 «нельзя опубликовать некорректные обязательные данные»: «обязательный» нужно определить — тариф обязателен только для позиций с признаком «участвует в расчёте».)

**Решение владельца Q5 (подтверждено 2026-11-13):** разрешены предварительные категории и записи без тарифа; такие позиции не должны участвовать в расчёте; отсутствующий обязательный тариф не должен превращаться в нулевую стоимость; такие позиции отражаются в диагностике. Следствие для §15.5: «обязательный тариф» — для позиций, участвующих в расчёте; для предварительных — предупреждение.

### Вопрос 6. RBAC (§13) — приоритет CA-T-602/603

§13 требует «только авторизованные с правами». Сейчас guard-заглушка CA-T-501 («полноценная auth/RBAC — CA-T-602/603»). Развёртывание админки с каталогами и массовыми операциями без RBAC повышает риск.

**Вопрос владельцу:** включать ли CA-T-602/603 (RBAC) в Этап 1 как обязательное предусловие — или отложить до появления массовых операций (Этап 2)?

**Решение владельца Q6 (подтверждено 2026-11-13):** Этап 1 не расширяется механизмом авторизации; CA-T-602 и CA-T-603 остаются блокирующими для безопасной публикации; публикация в production не описывается как безопасная до выполнения этих блокеров. Статусы задач в плане не изменяются настоящим документом. Фактический контекст: код CA-T-602/603 отмечен DONE в плане (v0.77–v0.78, 2026-11-10); deployment-предусловия ADR-02 (Keycloak provisioning, issuer, секреты, live login) остаются OPEN (план v0.84) — до их закрытия блокер не считается выполненным.

### Вопрос 7. Единицы «комплект/пара/кг» (§3.2)

**Вопрос владельцу:** подтверждаются ли эти единицы как реально используемые (для направляющих «пара/комплект», для стали «кг») — расширение `unit` затронет импорт, валидацию связей и борд? (Если единицы не нужны для существующих позиций — расширение можно отложить; если нужны для новых категорий §6 — включить в Этап 1.)

**Решение владельца Q7 (подтверждено 2026-11-13):** набор `unit` не расширять до подтверждения конкретных потребностей; «комплект», «пара», «кг» и другие единицы заранее не добавляются.

### Статусы остальных позиций документа (не подтверждены владельцем)

- Все семь вопросов §16 (Q1–Q7) — **подтверждены** (2026-11-13) и зафиксированы в §3.1, §3.3, §4.1, §6, §7, §9.1, §12, §15 и §16 настоящего документа; те же решения отражены в ТЗ (`CALCULATION_ADMIN_TECHNICAL_SPECIFICATION.md` §12.5).
