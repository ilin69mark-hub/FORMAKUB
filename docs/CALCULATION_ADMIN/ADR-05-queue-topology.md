# ADR-05 — Очередь пересчёта и топология приложения

- **Статус:** **ACCEPTED / APPROVED** (решение владельца 2026-11-10: single-instance + in-process worker)
- **Статус реализации:** **IMPLEMENTED** для single-instance; multi-instance отложен
- **Дата:** 2026-11-10
- **Основание:** Q2/OI-051, OI-061, R-03 (решение владельца 2026-11-06), дизайн §13.3/§13.9/§16.5
- **Связанные задачи:** CA-T-401 (ADR) — **DONE**, CA-T-403–411 (jobs/worker/reconciliation) — **DONE**, CA-T-608 (instance lock) — **DONE**

## Контекст

Текущая версия работает на SQLite/файловом Storage Adapter. Блокировки операций (`withFileLock`) и rate-limit реализованы in-process через `Map`, поэтому они сериализуют работу только внутри одного процесса. Горизонтальное масштабирование без внешней очереди и распределённого лока приведёт к гонкам записи, повторной обработке заданий и нарушению инвариантов публикации/пересчёта.

Владельцем уже принято решение R-03: **один экземпляр приложения**, in-process блокировки, защита от второго экземпляра lock-файлом и heartbeat; многопроцессная топология сейчас не выбирается.

## Решение

1. **Топология v1 — single-instance.** Приложение запускается ровно в одном экземпляре (`replicas: 1`); общий том между экземплярами запрещён.
2. **Очередь — in-process worker + идемпотентная сверка.** Внешняя очередь (Redis/BullMQ и аналоги) для v1 не вводится. Worker является частью процесса приложения; восстановление после рестарта обеспечивается heartbeat/recovery и reconciliation.
3. **Защита от второго экземпляра — lock-файл.** `instance-lock.ts` захватывает лок с `O_EXCL`, `bootId` и heartbeat; живой второй экземпляр отклоняется, остаточный лок снимается по TTL. При нескольких инстансах `withFileLock`/rate-limit не являются межпроцессной защитой.
4. **Параметры worker (утверждены в CA-T-404):** heartbeat — 10 с, stale — 30 с, максимум восстановлений — 3; далее `dead_letter`. Runtime-сверка выполняется при старте worker и далее с периодом по умолчанию 60 с (`FORMAKUB_RECALC_RECONCILE_MS`); это эксплуатационный параметр реализации, а не новое архитектурное значение.
5. **Границы worker и жизненный цикл задания.** Worker является частью процесса приложения и отвечает за полный жизненный цикл `ProjectRecalculation`:
   - идемпотентная сверка (`reconcileRecalculationState`) при старте и периодически;
   - восстановление зависших `running`-заданий (stale → `pending` либо `dead_letter`);
   - атомарный захват `pending → running` (единственный победитель; проигравший не пишет);
   - выполнение пересчёта **существующим** сервисом `recalculateProject` (DataResolver → Engine → Display Adapter → атомарная запись проекта/истории), без второго механизма расчёта;
   - проверка apply gate §10.5 до записи (source/calcVersion/superseded/ALREADY_AT_TARGET);
   - heartbeat во время выполнения;
   - закрытие задания `completed` / `failed` / `skipped` / `cancelled` / `dead_letter`;
   - retry-политика: retryable-ошибка → `failed → pending`, пока `attempt < maxAttempts`; исчерпание → `dead_letter`; non-retryable → `failed`.
6. **Один worker на процесс.** Runtime-worker создаётся singleton-функцией `startRecalculationRuntimeWorker`; повторный запуск возвращает существующий экземпляр. Остановка — `stopRecalculationRuntimeWorker` по `SIGTERM`/`SIGINT`/`beforeExit`.
7. **Публикация и пересчёт при нескольких инстансах запрещены** до перехода на multi-instance-архитектуру.
8. **Multi-instance отложен.** Переход требует одновременно: внешней очереди, распределённого лока, пересмотра хранилища (SQLite/файлы как single-writer) и отдельного ADR/решения владельца. Частичный переход не допускается.

## Последствия

- Для v1 достаточно существующих `jobs.ts`, `worker.ts`, `reconcile.ts`, `instance-lock.ts`; внешняя инфраструктура не требуется.
- `worker.ts` подключён к runtime через `src/instrumentation.ts`: после успешного захвата instance lock запускается единственный in-process worker; остановка — по сигналам процесса.
- `FORMAKUB_RECALC_WORKER=0` отключает worker (эксплуатационный выключатель); по умолчанию worker включён вне `NODE_ENV=test`.
- Ограничения фиксируются в эксплуатационном регламенте: один экземпляр, один владелец тома, запрет шаринга, `replicas: 1`.
- Rate-limit и `withFileLock` остаются in-process и корректны только в рамках single-instance.
- При появлении требования горизонтального масштабирования ADR-05 пересматривается до запуска второго экземпляра.

- [x] In-process worker с heartbeat/recovery реализован (CA-T-404).
- [x] Worker выполняет полный жизненный цикл pending-задания: claim → recalc → apply gate → close/retry (CA-T-404).
- [x] Идемпотентная сверка реализована и вызывается в runtime (CA-T-408).
- [x] Запрет multi-instance зафиксирован в документации и конфигурации.
- [x] Подпись владельца (CA-T-401, 2026-11-10).
