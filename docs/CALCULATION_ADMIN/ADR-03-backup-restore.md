# ADR-03: Persistence рантайма — backup и восстановление

- **Статус:** утверждён владельцем 2026-11-07
- **Задача:** CA-T-102 (`CALCULATION_ADMIN_IMPLEMENTATION_PLAN.md`, Фаза 1); основание — прямое решение владельца (пакет «CA-T-101 / CA-T-102», Q3/OI-060)
- **Затрагивает:** дизайн §13.7–§13.8, §16.1 (реестр ADR); ТЗ T-0.3, R-03, Q-12
- **Вопрос ADR (дизайн §16.1):** volume/backup для данных приложения (сегодня volume отсутствует — **[ФАКТ]** OI-039)

## Статус сверки (2026-11-10)

- **Архитектурный статус:** **ACCEPTED** (утверждён владельцем 2026-11-07).
- **Статус реализации:** **PARTIAL**.
- **Подтверждено:** постоянный Docker volume; часовой backup; WAL-aware снимок; `PRAGMA integrity_check`; ротация 48/30/12; `restoreDatabase`; S3-совместимые настройки в Compose/env; single-instance lock.
- **Restore-drill (2026-11-10, изолированно):** выполнен на временной копии: backup активной SQLite → restore в отдельный каталог → `integrity_check` = `ok` → чтение данных через Storage Adapter; исходная backup-копия сохранена. Тест: `src/lib/server/storage/restore-drill.test.ts` (passed). Production `data/formakub.db` не затрагивалась.
- **Остаётся:** ежеквартальный production restore-drill в отдельной среде фактически не проведён (изолированный drill его не заменяет); внешние S3-копии включаются только при полном наборе `S3_*` (сейчас не настроены — GAP деплоя); механизм/глубина хранения исторических сборок движка не определены; retention истории Q13 и архив Q14 — отдельные решения.
- **Связанные задачи:** CA-T-102/608/006 — DONE; локальный restore-drill — DONE (2026-11-10); production/quarterly drill остаётся эксплуатационной OPEN-процедурой.

## Решение (утверждено владельцем)

| Параметр | Решение |
|---|---|
| Частота backup | Каждый час |
| RPO | Не более 1 часа |
| RTO | Не более 4 часов |
| Почасовые копии | 48 |
| Ежедневные копии | 30 дней |
| Ежемесячные копии | 12 месяцев |
| Хранение | Внешнее S3-совместимое хранилище |
| Проверка | Автоматическая проверка целостности |
| Restore-drill | Ежеквартально |

## Дополнительные требования (утверждены владельцем)

- Backup SQLite учитывает **WAL** (снимок согласованной базы, а не «сырого» файла).
- **Не копировать работающую базу простым копированием файла.**
- Резервные копии хранятся **вне рабочего Docker volume**.
- **Исторические версии расчётного движка**, необходимые для воспроизводимости расчётов (§5.7 дизайн-документа, R-05/CA-Q-001), **входят в резервирование**.
- Восстановление проверяется **в отдельной среде**.

## Последствия

- Для данных приложения требуется постоянный Docker volume; сама реализация volume/backup в `docker-compose.yml` и запуск регламента — **отдельная задача CA-T-608** (в объём CA-T-102 не входит: конфигурация приложения настоящей задачей не изменяется).
- Restore-drill — ежеквартальная процедура с подтверждением читаемости проектов, активности прайсов и наличия истории (сверка §13.4 после восстановления).
- Параметры retention копий (48/30/12) и внешнее S3-хранилище обязательны для приёмки эксплуатации (DoD Фазы 1: «volume/backup проверены»).

## Не решается настоящим ADR

- Настройки самого приложения и Compose (объём, имена, доступы) — реализация CA-T-608;
- **механизм и глубина хранения исторических сборок расчётного движка** — в резервирование включены (п. выше), но способ хранения и глубина настоящим ADR **не определены** — отдельное открытое решение (не блокирует CA-T-103);
- retention данных панели (Q13) — открытый вопрос; формат/механизм архива (Q14; политика «архив, не удаление» утверждена R-02) — отдельное решение.
