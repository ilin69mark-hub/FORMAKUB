## 2. Контекст и проблема

**[ФАКТ]** Решение владельца Q1 (2026-11-13) утверждает четыре принципа:

1. управляемые нормы комплектации находятся в отдельном слое данных;
2. формулы и алгоритмы расчётного ядра остаются в коде;
3. второй расчётный движок не создаётся;
4. изменения управляемых правил учитываются в версионировании и воспроизводимости расчётов.

**[ФАКТ]** Сегодня нормы комплектации разнесены минимум по трём местам — код, content-константы и (частично) параметрический manifest — что прямо зафиксировано в `ADMIN_TARGET_STRUCTURE_RECONCILIATION.md` §7 («Нормы разнесены по трём местам — ровно то, что §7 [целевой модели] запрещает») и в `MODULE_AND_COMPONENT_INVENTORY.md` §9 (п.17: дублирование `content/*` ↔ snapshot, `SINK_RULES` ↔ manifest, `config.supports` ↔ `SUPPORT_SYSTEMS`).

**Проблема версионирования.** Существующая модель (`CALCULATION_ADMIN_DATA_AND_VERSIONING_DESIGN.md` §5.2) относит «изменение … комплектации (включая правку констант, участвующих в формулах: `SINK_RULES`, допуски опор, пороги)» к **`calcVersion` и только разработке**. Q1 переносит эти нормы в данные, изменяемые без релиза кода. Таким образом, изменение норм перестаёт быть «изменением алгоритма сборки» и должно получить явное место в модели версий — иначе либо нарушается правило A6/§5.2, либо нарушается требование Q1 «учитывать изменения в версионировании и воспроизводимости». **Это и есть главный архитектурный вопрос настоящего ADR (§6).**

**[ВЫВОД]** Существующая инфраструктура версий (черновик → валидация → публикация → снимок → фиксация в `StoredProject`/`ProjectPriceHistory` → fail-closed разрешение в `DataResolver`) уже решает задачу воспроизводимости для цен. Вопрос ADR-07 — как распространить этот принцип на нормы комплектации, не смешивая их с ценами и не ломая утверждённые правила.

## 4. Архитектурные требования

1. **[из Q1]** Отдельный слой данных для управляемых норм; формулы/алгоритмы — только в коде; один расчётный движок.
2. **[из Q1]** Любое изменение управляемой нормы должно фиксироваться версией и обеспечивать воспроизводимость: по проекту/записи истории определяется, какие нормы применялись.
3. **[A5/ADR-06 §9.1]** Изменение норм не должно молча менять расчёты существующих проектов; `config` проекта не изменяется ничем, кроме пользователя.
4. **[A7]** Автоматический пересчёт при публикации цен остаётся операцией «только стоимость»; пересчёт норм — отдельно определённое поведение.
5. **[A6/дизайн §5.2]** Изменение алгоритмов/формул — `calcVersion`, только релиз; перенос норм в данные не должен позволять правку кода «через админку».
6. **[ADR-06 §4, §7]** `DataResolver` — единственная сборка входов; whitelist входов движка, без wildcard; неизвестный атрибут → fail-closed.
7. **[ADR-06 §5.6]** Фактические версии штампуются в `CalculationResult.versions` и сохраняются в `StoredProject`/`ProjectPriceHistory`.
8. **[R-14, CA-T-208]** Новые `PriceItem` — только контролируемым импортом; импорт создаёт draft, публикация отдельна. Правила Q1 не вводят параллельный механизм создания цен.
9. **[Q5, 2026-11-13]** Предварительные записи без подтверждённого тарифа не участвуют в расчёте; отсутствующий обязательный тариф ≠ нулевая стоимость; отражаются в диагностике.
10. **[Q7]** Единицы измерения — только существующий `enum unit`; новые не вводятся без подтверждения.
11. **[Q6]** Административный контур остаётся под ADR-02: публикация в production не безопасна до выполнения CA-T-602/603.
12. **[совместимость]** Кухонный и шкафной калькуляторы продолжают работать через один контракт (`config.kind` определяет ветку); правила имеют область применения `kitchen|wardrobe|shared`.
13. **[A3]** Админка не исполняет формулы; движок не принимает исполняемый код.

## 6. Варианты решения (главный вопрос — версионирование)

### Вариант A. Правила входят в `PricingVersion`

**Логическая модель:** нормы комплектации — часть коммерческого снимка: либо расширение `PriceRulesInput` (сейчас 6 ключей), либо отдельный массив правил внутри `PricingVersion` (наряду со `snapshot`/`rules`/`promos`), попадающий в `priceSnapshot` снимка.

- **Изменение `CalculationInputs`:** пятой отдельной группы нет; расширяется `priceSnapshot` (существующая группа). Контракт `PriceRulesInput` расширяется явно; неизвестные поля по-прежнему отклоняются (ADR-06 §7.4) → **старые снимки без правил требуют явной нормализации** (политика зафиксирована предварительным решением Q7-02: legacy без версии правил — блокировка расчёта, чтение сохранено; §11.3). *Вариант не выбран владельцем (Q7-01а → B).*
- **Связь с `DataResolver`:** без изменений — уже копирует `version.rules`/`snapshot` в inputs (`data-resolver.ts` §сбор snapshot). Новых разрешений нет.
- **Публикация и snapshot:** правила публикуются тем же draft → `validateDraftVersion` → publish; Diff получает targetType правил (как сейчас `rule`/`promo`). Snapshot версии становится самоценным носителем норм.
- **`StoredProject` / `ProjectPriceHistory`:** без изменений — `priceVersion` уже пинит все потреблённые движком данные снимка.
- **Совместимость старых проектов:** высокая при явном правиле нормализации, но вариант **не выбран** (Q7-01а → B); для выбранного B действует политика блокировки расчёта при сохранении чтения (Q7-02, §11.3).
- **Автоматический пересчёт:** применяет новые правила автоматически вместе с новым прайсом (правило «только Commercial Snapshot» формально соблюдено, если правила — часть снимка).
- **Миграции/тестирование:** импорт норм из кода (паттерн R-14/CA-T-208: контент → draft → публикация), паритет-тесты «данные ≡ текущие кодовые значения», расширение `PriceRulesInput` + fail-closed тесты, golden без изменений формул.
- **Сложность/риски:** **низкая/средняя**. Риски: смешение цен и норм (diff правил выглядит как изменение прайса); изменение количества комплектующих = «изменение цены» в аудите; публикация правил запускает пересчёт проектов, что визуально и семантически равно публикации цен; **требует пересмотра классификации дизайна §5.2** (сейчас «комплектация → calcVersion») — отдельное утверждение владельца; старые снимки без правил.

### Вариант B. Правила в версионируемых `CalculationInputs`, но не в `PricingVersion`

**Логическая модель:** нормы — отдельный снимок правил со своей версией (`rulesSnapshot { versionId, rules[] }`), не коммерческая сущность. Версия правил фиксируется в расчётном пакете, штампуется в результате и сохраняется у проекта/в истории.

- **Изменение `CalculationInputs`:** добавляется пятая группа `rulesSnapshot` (по образцу `priceSnapshot`: `versionId` + данные); типизация и whitelist расширяются по правилам ADR-06 §7 (fail-closed, без wildcard).
- **Связь с `DataResolver`:** DataResolver разрешает правила по версии проекта/операции (по образцу разрешения прайса и pins); недоступная версия правил → fail-closed (как отсутствующая `priceVersion`).
- **Публикация и snapshot:** правила публикуются отдельной операцией (draft → валидация связей → publish в собственной сущности-снимке); публикация правил **не** является публикацией прайса и не обязана запускать прайс-пересчёт.
- **`StoredProject`:** поле-ссылка на версию правил (аналог `priceVersion`, `optional` по правилам design §5.6.3); **`ProjectPriceHistory`:** запись версии правил наряду с `priceVersion`/`calcVersion`.
- **Совместимость старых проектов:** отсутствие версии правил обрабатывается по явной политике — **решено предварительно: блокировка расчёта при сохранении чтения** (Q7-02, §11.3); старые проекты не получают новых норм молча.
- **Автоматический пересчёт:** фиксирует `priceVersion` **и** `rulesSnapshotId` (закрепление проекта); изменение правил не применяется к существующим проектам автоматически — **решено предварительно: pinned** (Q7-01б, §11.2); применение новых норм — новые проекты либо отдельная операция перехода (контракт — §11.5, решение Q7-11).
- **Миграции/тестирование:** импорт норм из кода (draft → публикация); паритет-тесты; расширение DataResolver + контракта; optional-поля проекта/истории (без нарушения strictObject — design §5.6.3); тесты воспроизводимости «старый проект + старая версия правил».
- **Сложность/риски:** **средняя**. Риски: два независимых снимка (цен и правил) → сложность операционной согласованности; политика отсутствующей версии правил; расширение контракта (5-я группа) требует явного утверждения ADR-06-совместимости; нужно определить, как версия правил попадает в историю и инспектор.

### Вариант C. Отдельная `rulesVersion` (полноценная третья версия)

**Логическая модель:** правила — самостоятельный версионируемый домен наряду с `schemaVersion`/`calcVersion`/`priceVersion`: собственная сущность-версия, собственный жизненный цикл публикации, отдельные триггеры применения.

- **Изменение `CalculationInputs`:** как в B (пятая группа `rulesSnapshot`), но версия правил — публичное поле модели.
- **Связь с `DataResolver`:** четвёртое разрешение (прайс, каталоги, параметры, **правила**); preflight и коды ошибок расширяются.
- **Публикация и snapshot:** независимая публикация правил: правка норм → draft правил → валидация → publish **без** публикации прайса; возможно рассинхронное состояние «цены новые, правила старые» → матрица допустимых комбинаций.
- **`StoredProject`:** поле `rulesVersion`; **`ProjectPriceHistory`:** поле `rulesVersion`; **`CalculationResult.versions`:** расширение четвёртой версией.
- **Совместимость старых проектов:** полная матрица совместимости (как для `calcVersion`/`priceVersion`, дизайн §5.7): отсутствие версии → явная политика; миграция записей optional-полями.
- **Автоматический пересчёт:** остаётся «только Commercial Snapshot»; изменение правил — отдельный тип операции пересчёта (не прайс) со своей аудируемой историей.
- **Миграции/тестирование:** расширение `StoredProject`/`ProjectPriceHistory`/`CalculationResult` (правила design §5.6.3 и классификации §5.2 — пересмотр); миграции чтения; полный набор: паритет, воспроизводимость, матрица комбинаций «цены × правила», обратная совместимость.
- **Сложность/риски:** **высокая**. Риски: расширение утверждённой модели трёх версий (требует явного решения); рост числа сценариев совместимости и пересчёта; соблазн независимых публикаций «не в ту сторону»; наибольший объём миграций и тестов; существующие open issues (CA-RISK-002, исторические сборки) касаются и новой версии.

## 8. Рекомендуемый вариант

**[РЕКОМЕНДАЦИЯ]** Принять **Вариант B** как основу для утверждения.

Обоснование:

1. **Единственный вариант, где «норма ≠ цена» по построению.** Q1 требует отдельный слой правил; вариант A физически складывает нормы внутрь коммерческого снимка, из-за чего изменение количества петель проходит аудиторски как изменение прайса — что противоречит смыслу разделения, зафиксированному в решении Q4 (цены и только цены — `PricingVersion`) и в целевой модели (§7: «нельзя хранить одну норму в каталоге, другую в коде» — и подразумевает норму как самостоятельную сущность, а не как атрибут цены).
2. **Соответствие A5 и правилу воспроизводимости.** В B версия правил фиксируется у проекта и в истории, как `priceVersion`; изменение норм не молча меняет старые проекты. В A новые нормы применяются к старым проектам при ближайшем прайс-пересчёте — это требовало бы явного пересмотра правила «изменения не меняют старые проекты».
3. **Экономия относительно C.** B не вводит четвёртую публичную версию в модель трёх версий, не создаёт матрицу комбинаций «цены × правила» и не требует расширения всех моделей сразу; при этом вся механика (draft → валидация → publish → снимок → версия → fail-closed) копирует **уже проверенный** путь `priceVersion`, а не изобретается заново — риск ниже, чем у C при сопоставимой достигаемости.
4. **Сохранение A7/A6.** Авто-пересчёт остаётся «только стоимость + закреплённые нормы»; правка кода (`calcVersion`) и правка данных правил (`rulesSnapshotId`) разведены — ни одно не подменяет другое.

**Компромиссы, которые принимаются с B:** расширение контракта входов пятой группой (требует явной зафиксированной совместимости с ADR-06); политика для старых записей без версии правил; два снимка, которые нужно показывать согласованно в админке и инспекторе.

**Когда выбрать A вместо B:** если приоритет владельца — минимальный объём изменений и **автоматическое применение** новых норм при следующем пересчёте (тогда правка §5.2-классификации и риски смешения осознанно принимаются).

**Когда выбрать C вместо B:** если владельцу нужна независимая публикация норм (правила меняются по своему календарю, без прайса) и полное разделение жизненных циклов — тогда стоимость C (расширение модели трёх версий) оправдана.

**Статус (предварительное решение, 2026-11-13):** владелец предварительно выбрал **вариант B** (Q7-01а, §1.1); альтернативы A и C сохранены в §6–§7 как проведённый анализ. Утверждение ADR-07 вместе с этим выбором — отдельное решение владельца (§18).

## 10. Контракт взаимодействия с движком

### 10.1. Условия применимости: как хранить

**[ПРЕДЛОЖЕНИЕ]** Фиксированный набор предикатов (декларативные структуры), а не выражения/скрипты:

- белый список операторов: `equals`, `notEquals`, `in`, `greaterThan`, `lessThan`, `all/any` (комбинации с ограничением глубины);
- белый список предметов условия: `kind` (kitchen/wardrobe), `moduleType` (8 типов), `zone`, `option` (флаг конфигурации, напр. `pushToOpen`, `plinth`), `material`/`facadeStyle`/`handle`, `dimension` (ширина/высота/глубина против порога), `attribute` каталоговой позиции;
- ссылки (`ref`) на сущности — только по `id` существующих каталогов, fail-closed.

Обоснование: **все фактические условия AS-IS (класс 2, §3.2) выражаются этим набором** (тип изделия, тип модуля, зона, флаги, выбор материала/стиля/ручки, пороги по ширине/габариту, наличие опции). Это исключает произвольный код и «конструктор программ» при полном покрытии текущих правил.

**Запрещено на уровне ADR:** произвольные выражения, шаблоны кода, вычислимые пользователем формулы. Расширение выразительности — только через отдельный ADR с оценкой безопасности.

**[УТВЕРЖДЕНО Q7-03, решение по C-1]** белый список выше утверждён как закрытая граница выразительности:

- **Операторы:** `equals`, `notEquals`, `in`, `greaterThan`, `lessThan`, `all`, `any`.
- **Ограничения сложности:** глубина вложенности ≤ 2; ≤ 8 предикатов на одно правило. Отрицание — только через `notEquals`; диапазон — только композицией `all(greaterThan, lessThan)`.
- **Предметы условия:** `kind`, `moduleType`, `zone`, `option`, `material`, `facadeStyle`, `handle`, `dimension`, `attribute`, `ref` (по `id` существующих каталогов, fail-closed).
- **Типы значений:** `int`, `decimal`, `boolean`, `enum`, `string[]`.
- **Поведение при нарушении:** неизвестный оператор/поле/тип значения → ошибка валидации при публикации (`ValidationResult.passed=false`, ADR-02) и fail-closed при разрешении/исполнении — условие никогда не исполняется «в обход» (§10.4 п.7).
- **Произвольный DSL и выполнение пользовательского кода не допускаются.** Любое расширение whitelist — только отдельным ADR.

### 10.2. Трассировка для расчётного инспектора

Минимальный контракт, достаточный для ответов §10 целевой модели («какое правило сработало / почему / откуда количество / какая комплектующая / откуда цена / какие версии»):

1. **Статическое соответствие «правило → строка результата»:** каждое правило ссылывается на `CalculationLineId` (33 существующих id, `contract.ts:188–200`) через `assigns.line`. Соответствие детерминировано кодом — отдельное хранение трассы не требуется (паттерн `display-metadata` уже хранит «строка → как показать»; здесь добавляется «строка → какое правило»).
2. **Количество:** для строк, где количество определяется нормой, payload строки расширяется ссылкой `ruleId` (и значением нормы); для строк, где количество — формула (периметры, длины), ссылки нет — объяснение даёт формула (§10 целевой модели: «реестр формул» уже существует).
3. **Версии:** `CalculationResult.versions` += **`rulesSnapshotId` (идентификатор снимка правил, вариант B — не «четвёртая версия»**, §11.1 п.5); `ProjectPriceHistory` хранит те же идентификаторы (уже хранит `calcVersion`/`priceVersion`, `types.ts:387–404`).
4. **Тариф:** цена строки — из `priceSnapshot` (`priceItemId` → `amount`), уже доступна; инспектор показывает `priceItemId` + `priceVersion`.
5. **Причина применения:** `condition` правила исполняется движком/слоем входов; для объяснения инспектору возвращается/сохраняется результат разбора условия (какие предметы условия сработали) — контракт: отдельная read-only структура `LineExplanation` в ответе инспектора, **не** в `CalculationBreakdown` (не расширяет утверждённый результат расчёта без отдельного решения).

**[ВЫВОД]** Хранить полную трассу каждого расчёта не требуется: достаточно (а) идентификатора снимка правил в результате/истории, (б) статического соответствия правило → lineId, (в) унаследованной из snapshot привязки строки к тарифу, (г) read-only пояснения условия для инспектора.

### 10.3. Границы слоёв (сохраняются ADR-06 §4)

| Слой | Действия с правилами |
|---|---|
| Calculation Admin | редактирование/публикация правил (черновик), диагностика; **не** исполняет формулы |
| DataResolver | разрешение `rulesSnapshotId` → группа `rulesSnapshot` в inputs; проверки ссылок/полноты; **не** считает |
| Engine | исполняет формулы (код) с нормами из inputs; штампует версии; **не** читает хранилище; при отсутствии обязательного правила/тарифа — fail-closed, не ноль |
| Operation Layer | preflight версий (цена + правила), фиксация в истории |

### 10.4. Техническая согласованность: `rulesSnapshotId` через контракт

**[УТВЕРЖДЕНО на уровне архитектуры]** логический контракт согласован; физическое хранение снимков — вне настоящего документа (§5). Пятая группа `CalculationInputs.rulesSnapshot` согласована с ADR-06 минимальным addendum §5.3 (остальные решения ADR-06 не пересматриваются).

1. **Как `rulesSnapshotId` передаётся через `CalculationInputs`.** Пятая группа входов: `rulesSnapshot: { rulesSnapshotId: string; rules: ManagedRule[] }` — по образцу `priceSnapshot: { versionId, snapshot, rules, … }` (ADR-06 §5.3: четыре группы → пять). Идентификатор входит в группу правил и **не дублируется** вне `inputs` (как `priceVersion` не является отдельным полем inputs — дизайн §9.4.2). Состав `rules` — разрешённое содержимое снимка; `rulesSnapshotId` — его однозначный идентификатор.
2. **Как `DataResolver` разрешает снимок:**
   - `create`/`preview` → **активный опубликованный** снимок правил на момент разрешения (по образцу правила ADR-06 §5.1 для прайса);
   - расчёт/повторный расчёт существующего проекта → снимок по **`StoredProject.rulesSnapshotId`** (закрепление, §11.2); выбор цен — независимо, по действующим правилам `targetPriceVersionId`.
   Разрешение — только из хранилища; «живые»/draft/preliminary-записи никогда не читаются.
   **[ФАКТ — точный аналог уже существует на стороне цен]:** выбор версии прайса для существующего проекта реализован как `input.targetPriceVersionId ?? project.priceVersion` (`data-resolver.ts:740`), при этом цель обязана быть `published` (`data-resolver.ts:798–803`), несовпадение цели с `published` и отсутствие версии → контролируемая ошибка (`data-resolver.ts:745–777`). Pinned-логика правил проектируется как зеркальная к этому механизму, а не как новая семантика.
3. **Где хранится закреплённый snapshot проекта:** `StoredProject.rulesSnapshotId` (ссылка); сам снимок — в хранилище правил как неизменяемая запись. Физический носитель/коллекция — вне ADR (§5); поле — optional-метаданные-ссылка, `schemaVersion` не повышается (решение Q7-07, §14.4).
4. **Как snapshot фиксируется в `ProjectPriceHistory`:** отдельная запись `rulesSnapshotId` в каждой записи истории (рядом с `calcVersion`, `priceVersion`, `breakdown` — `types.ts:387–404`); это **факт расчёта** и не заменяет закрепление проекта (§11.2 — две разные ссылки).

Физическая схема/формат хранения снимков — вне настоящего ADR (§5) и определяется при реализации.

## 11. Версионирование и воспроизводимость

**[ПРЕДВАРИТЕЛЬНОЕ РЕШЕНИЕ Q7-01а]** выбран **вариант B**: неизменяемый снимок правил идентифицируется отдельным **`rulesSnapshotId`**; полноценная самостоятельная система `rulesVersion` **не вводится** (§1.1, §6–§8).

**[ФАКТ → правило]** Утверждённые ограничения сохраняются: `schemaVersion`/`calcVersion`/`priceVersion` остаются тремя версиями; ADR-07 **не создаёт четвёртую публичную версию в модели**: `rulesSnapshotId` — идентификатор данных снимка правил, а не новая версия в модели версий (вариант C с `rulesVersion` — не выбран).

### 11.1. `rulesSnapshotId` — определение и требования (решение Q7-01а)

`rulesSnapshotId` — идентификатор **неизменяемого снимка опубликованных правил комплектации** (полного набора `ManagedRule`, см. §9).

Требования:

1. **`rulesSnapshotId` не подменяет `priceVersion`.** `priceVersion` остаётся исключительно коммерческим идентификатором (`PricingVersion`); правила и цены идентифицируются раздельно и публикуются независимо. Снимок правил не хранится внутри `PricingVersion` и не заменяет её (вариант A отвергнут выбором).
2. **Однозначность и полнота содержимого снимка:** снимок содержит **полные копии содержимого** опубликованных правил (все поля §9 каждого правила со `status=published` на момент публикации) — **не ссылки и не списки идентификаторов изменяемых записей каталога**. Состав и содержимое снимка детерминированы по `rulesSnapshotId` (паттерн: снимок = полная копия — по аналогии с `PricingVersion.snapshot`, дизайн §8.3 «снимок, не ссылки»). **Гарантия сценария S1→S2:** после изменения правила R1 и публикации нового снимка S2 проект, закреплённый за S1, продолжает получать **первоначальное содержимое R1** из S1; повторная публикация R1 не переписывает S1 (§11.1 п.3–4, §11.2).
3. **Неизменяемость:** опубликованный снимок после публикации не изменяется (паттерн «опубликованная версия неизменяема», spec §4.3).
4. **Изменение → новый снимок:** правка любого опубликованного правила создаёт новую редакцию правила **и** новый `rulesSnapshotId`; прежний снимок сохраняется нетронутым для пиннинга и истории.
5. **Без `rulesVersion`:** не вводится четвёртая версия в модель `schemaVersion`/`calcVersion`/`priceVersion`; не создаётся параллельный жизненный цикл «версий правил» как публичной сущности — только снимки-данные с идентификатором.
6. **Независимость версионирования цен и правил:** публикация правил не меняет `priceVersion`; публикация прайса не создаёт снимок правил; ни одна из операций не требует другой (см. §12).
7. **Формат идентификатора (закрыто технически):** `rulesSnapshotId` — **непрозрачный уникальный неизменяемый строковый ключ**, без семантического содержания. **[ФАКТ]** точный аналог уже применяется: идентификаторы записей в контуре прайса генерируются как `randomBytes(8).toString("hex")` (`publish.ts:198`), а схема `pricingVersionSchema.id` — просто `nonEmptySchema` с комментарием «`price-YYYY.MM.N` — формат [ПРЕДПОЛОЖЕНИЕ], не нормируется» (`admin/schema.ts:206–210`). Следствие: и для `rulesSnapshotId` человекочитаемый формат не нормируется, уникальность обеспечивается генератором, неизменяемость — правилом п.3–4; смена id не предусмотрена (id — ключ ссылок конфигураций/истории, §9).
8. **Хранение опубликованных снимков (решение Q7-10):**
   - снимок содержит **полную копию содержимого** всех опубликованных правил (не ссылки и не списки идентификаторов изменяемых записей — п.2);
   - опубликованный снимок **неизменяем**; изменение исходных редакций правил **не меняет** ранее опубликованные снимки (следствие п.2–4; сценарий S1→S2);
   - **физическое удаление снимка, на который ссылаются `StoredProject` или `ProjectPriceHistory`, запрещено**; хранение ранее опубликованных снимков — **бессрочное** (по образцу хранения `PricingVersion` со статусом `superseded`, `publish.ts:280–281`);
   - **валидация** снимка выполняется дважды: при публикации (структура, белый список условий, типы/единицы, связи, исключение `draft`/`preliminary` — §12) и при разрешении снимка в `DataResolver` (fail-closed, §10.4 п.5);
   - **целостность:** снимок содержит `contentHash` — канонический хеш полного содержимого правил; при разрешении хеш пересчитывается и сверяется, несовпадение → `RULES_SNAPSHOT_CORRUPT` (без подстановки).
9. **Неизменяемость опубликованной редакции (D-2):** запись правила со `status=published` не редактируется и не перепубликовывается; изменение — только создание **новой draft-редакции** (отдельная запись, `version` + 1) с последующей отдельной публикацией. При публикации новой редакции предыдущая опубликованная редакция той же линии переводится в `archived` (содержимое не меняется) и в новый снимок не входит.

### 11.2. Pinned для существующих проектов (решение Q7-01б)

Разделяются две разные ссылки:

| Ссылка | Что фиксирует | Где |
|---|---|---|
| **закрепление проекта** | текущий `rulesSnapshotId` — снимок, по которому выполняются все будущие расчёты проекта | `StoredProject.rulesSnapshotId` |
| **факт исторического расчёта** | `rulesSnapshotId`, использованный **именно этим** расчётом | `ProjectPriceHistory.rulesSnapshotId` (рядом с существующими `calcVersion`/`priceVersion`, `types.ts:387–404`) |

Правила:

1. Проект использует **закреплённый** `rulesSnapshotId` при каждом расчёте.
2. **Публикация нового снимка не изменяет существующие проекты** — их закрепление не переписывается (следствие A5).
3. **Повторный расчёт использует закреплённый snapshot** (вместе с закреплённой/целевой `priceVersion` по действующим правилам A7 — пересчёт меняет только стоимость, нормы остаются прежними).
4. **Переход проекта на другой snapshot возможен только через отдельную контролируемую операцию** — контракт утверждён (решение Q7-11, §11.5): атомарное изменение закрепления + `AdminAuditLog`, optimistic locking, идемпотентность; без автоматического и пакетного перерасчёта.
5. **История каждого расчёта фиксирует фактически использованный `rulesSnapshotId`** независимо от текущего закрепления проекта — запись истории не переписывается при последующих публикациях/переходах.
6. **Автоматическая миграция проектов на новые правила не вводится.**

### 11.3. Legacy без версии правил (решение Q7-02): чтение — разрешено, новый расчёт — запрещён

**Разрешено (доступ к историческим данным сохраняется):** открытие проекта; просмотр конфигурации; чтение сохранённого `PriceSnapshot` и сохранённой стоимости; просмотр `ProjectPriceHistory` и исторических данных.

**Запрещено:** новый расчёт без достоверного `rulesSnapshotId`; **автоматическое назначение проекту актуального snapshot**; **восстановление исторической версии правил по предположению** (по дате, по эпохе `priceVersion` и т.п.); молчаливая подмена (design §5.4).

**[ВЫВОД]** Блокировка расчёта не лишает пользователя доступа к сохранённым данным: чтение и отображение не требуют версии правил. **Решение Q7-11:** retro-процедура определения/подтверждения исторической версии для legacy-проектов **в v1 не вводится** — такие проекты остаются заблокированными для нового расчёта до отдельного будущего решения владельца; автоназначение версии запрещено (§11.5).

### 11.4. Правила версионирования (по решениям владельца)

1. Изменение текста/значений правила → новая редакция + новый `rulesSnapshotId`; старые снимки неизменяемы (паттерн `PricingVersion`).
2. Каждый расчёт фиксирует использованные версии: `CalculationResult.versions` += `rulesSnapshotId` → `StoredProject` (закрепление) → каждая запись `ProjectPriceHistory` (факт).
3. Обычный прайс-пересчёт проекта применяет **закреплённый** `rulesSnapshotId` и новую `priceVersion` (сохраняет A5/A7: ни цена, ни нормы не подменяются молча).
4. Применение новых норм к существующему проекту — только отдельная операция перехода (§11.2 п.4, §11.5; решение Q7-11); автоматический и пакетный перерасчёт не выполняются.
5. Legacy без `rulesSnapshotId` → блокировка нового расчёта с сохранением чтения (§11.3); молчаливая подмена запрещена (design §5.4).
6. Правка `AdminParameter`, читаемого движком, по-прежнему требует `pending_release`/`calcVersion` (design §5.7 Revision 1); правка данных правил `calcVersion` **не** требует (код-алгоритм не меняется) — разграничение «данные правил ↔ код» сохраняется.

**[ВЫВОД]** Требование Q1 «изменения учитываются в версионировании и воспроизводимости» выполняется: результат воспроизводится по **набору идентификаторов воспроизведения**: `schemaVersion` (**версия схемы данных**), `calcVersion` (**версия алгоритмов**), `priceVersion` (**версия тарифов**), `rulesSnapshotId` (**идентификатор снимка правил — не версия**, §11.1 п.5). Это идентификаторы четырёх разных предметов, а не четыре версии в одной модели; модель трёх публичных версий при этом не расширяется.

### 11.5. Операция перехода проекта на другой снимок (решение Q7-11)

**[УТВЕРЖДЕНО]** контракт контролируемой операции на уровне архитектуры (детали API — при реализации):

1. **Отдельная явная операция.** Переход выполняется только явной операцией привязки проекта к целевому `rulesSnapshotId`; никаких косвенных путей (публикация, авто-миграция) не существует.
2. **Предварительные проверки:** существование целевого снимка; его статус — опубликованный; валидность содержимого (§11.1 п.8); отличие от текущего закрепления.
3. **Optimistic locking:** изменение закрепления выполняется с проверкой `expectedVersion` записи проекта (паттерн `expectedVersion` → 409, `catalogs.ts:247–256`); конфликт одновременного изменения проекта → отказ без изменений.
4. **Атомарность и аудит (реализовано с учётом Storage Adapter):** изменение закрепления (`rulesSnapshotId` + `updatedAt`) и запись `AdminAuditLog` выполняются в согласованном порядке с журналом намерения `rules-transition-journal.json`:
   - журнал пишется до изменения проекта;
   - проект изменяется атомарно (одна коллекция);
   - аудит пишется после изменения; при ошибке аудита выполняется откат закрепления (проект возвращается в исходное состояние), ложный `result=ok` не создаётся;
   - при сбое между шагами незавершённая операция восстанавливается: если проект уже изменён — дописывается недостающий audit event; если нет — запись журнала удаляется. Восстановление выполняется перед каждой новой операцией (`recoverPendingRulesTransitions`).
   - **Ограничение:** межколлекционной транзакции Storage Adapter нет (SQLite — в пределах коллекции, JSON — без транзакций). Строгая атомарность — отдельная инфраструктурная задача **NEW-N3**; в текущей реализации она не заявляется.
5. **Идемпотентность и replay (реализовано):** повтор с тем же `operationId` возвращает **результат исходной операции** — `previousRulesSnapshotId`, `rulesSnapshotId` и `updatedAt` после перехода; текущее состояние проекта не возвращается (`project: null`). Последующие переходы не меняют replay предыдущей операции; повтор не изменяет проект и не создаёт дублирующих audit events. Другие параметры при том же `operationId` → 409. Переход на уже закреплённый снимок — no-op без записи аудита.
6. **Без перерасчёта:** автоматический и пакетный перерасчёт при публикации правил и при переходе **не выполняются** (§12 п.8); `ProjectPriceHistory` переход не изменяет — новая запись появляется только при следующем расчёте и фиксирует фактически использованный `rulesSnapshotId` (§11.2 п.5).
7. **Права:** операция требует `recalc.run` (решение Q7-04, §13) и фиксируется в `AdminAuditLog`.
8. **Legacy в v1:** проекты без `rulesSnapshotId` остаются заблокированными для нового расчёта (§11.3); автоназначение версии и retro-процедура **в v1 не вводятся** — восстановление расчётной способности legacy-проекта возможно только по отдельному будущему решению владельца.

### 11.10. Publication journal и recovery (D-10, D-11)

**[РЕАЛИЗОВАНО]** `rules-publication-journal.ts` (`rules-publication-journal.json`):

- инвариант: завершённая публикация всегда имеет audit `rule.publish` с `requestId=operationId`;
- **operationId обязателен для любой публикации:** если доверенный серверный клиент его не передал, он генерируется в сервисе; legacy-путь без journal отсутствует;
- журнал хранит operationId, выбор и expectedVersion, contentHash, snapshotId, фазу, auditEventId, результат recovery;
- при replay по существующему audit журнал при необходимости создаётся/дополняется до `completed` (проверка инварианта, а не просто возврат результата);
- повтор без operationId (или с тем же operationId) использует завершённую публикацию с тем же contentHash/selection: возвращает replay без нового snapshot/audit;
- порядок: journal prepared → snapshot (существующий по contentHash или новый) → promotion выбранных draft → audit → completed;
- сбой до snapshot → recovery закрывает запись как `aborted` (audit не создаётся);
- сбой после snapshot/до audit → recovery идемпотентно дописывает audit (и promotion), не создавая повторный snapshot;
- повторный replay проверяет инвариант snapshot → audit; повторный recovery не дублирует audit;
- recovery вызывается при старте приложения (`instrumentation.ts`) и перед каждой публикацией; фонового процесса нет; межколлекционная транзакция не заявляется (NEW-N3 не реализуется).

## 12. Публикация и пересчёт

**[УТВЕРЖДЕНО; реализовано]** Жизненный цикл (вариант B, D-2):

1. **Создание draft (решено Q7-05):** создание правил — **ручное**, с обязательным статусом `draft`. **Draft не участвует в расчёте.** Создание правил **не смешивается** со созданием `PriceItem`: R-14 остаётся без изменений. Публикация правил остаётся запрещённой как production-операция до закрытия CA-T-602/603/CA-T-511 (Q6, §13).
2. **Редактирование:** только `draft`; optimistic locking (`expectedVersion`), `AdminAuditLog`. Опубликованная редакция неизменяема; изменение — только через новую draft-редакцию (§11.1 п.9).
3. **Валидация:** структура (zod, fail-closed), белый список условий, типы/единицы, диапазоны `value`.
4. **Проверка связей и тарифов:** `assigns` → существующие `CatalogItem`/`PriceItem`/`CalculationLineId`; для правил с `affects.price` — **обязательный тариф**; `source=preliminary` отклоняется (Q7-06).
5. **Публикация:** отдельная операция с **явным непустым выбором** draft-правил (`id` + `expectedVersion` каждого); дубликаты, неизвестные, archived, устаревшие версии и `preliminary` отклоняются; авто-публикация всех draft запрещена. Перед публикацией — подтверждение diff (реализовано в API/UI CA-T-613: `POST /api/admin/rules/publish`, `expectedStateVersion`, `confirmed`). **Production-публикация заблокирована** серверным gate до CA-T-511 (D-9): production-маркер (`FORMAKUB_ENV=production`/`NODE_ENV=production`) без `FORMAKUB_RULES_PUBLICATION_ENABLED=1`, а также противоречивая/некорректная конфигурация → отказ. RBAC — `price.publish`; CSRF и rate-limit — существующие механизмы CA-T-604; журнал публикации и audit recovery — §11.10.
6. **Фиксация снимка:** публикация создаёт **неизменяемый** снимок с `rulesSnapshotId` и `contentHash` (§11.1 п.2/п.8); выбранные draft-правила переводятся в `published` (содержимое и `version` не меняются); предыдущая опубликованная редакция линии — в `archived`. Повторная публикация идентичного содержимого возвращает существующий снимок (`replay`) без дубликата и без повторного аудита; сбой между записью снимка и статусами восстанавливается повторным вызовом.
7. **Применение в новых расчётах:** DataResolver включает `rulesSnapshot` для create/preview по **активному опубликованному снимку правил** на момент разрешения.
8. **Существующие проекты:** применяют **закреплённый `rulesSnapshotId`** (§11.2); публикация не запускает перерасчёт; переход — §11.5. Автоматический и пакетный перерасчёт не выполняются.
9. **История и диагностика:** `rulesSnapshotId` в истории; diff правил; инспектор — §10.2 (N2, не реализован).

**[ВЫВОД]** Публикация правил **не** наследуется автоматически от публикации прайса: у них свой черновик, своя валидация связей и свой триггер применения. Предполагать идентичное поведение нельзя — это явно отдельное решение (задание §9).

## 13. Безопасность и валидация

- **[Q6/ADR-02] Права (решено Q7-04, по C-2):** правила — коммерчески значимые данные; используются **существующие permissions** без расширения ADR-02: **чтение** — действующие права просмотра (`calc-viewer`/`calc-admin`); **создание/редактирование draft** — `catalog.write`; **публикация** — `price.publish`; **переход проекта на другой снимок** — `recalc.run` (§11.5). **Все операции** (создание, редактирование, публикация, переход) фиксируются в `AdminAuditLog`; **перед публикацией — подтверждение diff** (§12 п.5). Новых ролей и прав (`rules.write`/`rules.publish`) не вводится; любое расширение permissions — только отдельной редакцией ADR-02. Публикация правил остаётся запрещённой до закрытия блокеров CA-T-602/603 (Q6, §1.1).
- **Fail-closed:** отсутствие обязательного правила/тарифа → ошибка расчёта, не нулевая цена (Q5; паттерн `priceRef`/`fail()` в `engine.ts`).
- **Запрет исполняемого кода:** только структурированные условия из белого списка (§10.1); валидация отклоняет неизвестные операторы/предметы (аналог «неизвестный ключ → fail-closed» ADR-06 §7.4).
- **Целостность:** проверка ссылок `assigns` при публикации; `status=archived` не удаляется при ссылках (R-10).
- **Предварительные нормы (решено Q7-06; решение Q5):** полное исключение из расчёта: предварительные записи **могут существовать в каталоге**, но **не попадают в опубликованный расчётный снимок**, **не передаются в `CalculationInputs`** и **не используются `DataResolver`**; отсутствие обязательного подтверждённого правила приводит к контролируемой ошибке — **без нулевого fallback и неявной подстановки**.
- **Аудит:** каждое изменение → `AdminAuditLog` (кто/что/до-после); публикация правил фиксируется отдельным типом события (паттерн `pricing.create`/`price.publish`).
- **Реализованный API/UI (CA-T-613):** чтение — `requireAdminApi` (любая админ-сессия); создание/редактирование draft и новая редакция — `catalog.write`; публикация — `price.publish`; переход проекта — `recalc.run`. Все мутации проходят общий guard CA-T-604 (same-origin + rate-limit). UI: `/admin/rules` (список, карточка, редакции, форма draft/редакции, выбор и подтверждение публикации, снимки, переход проекта).

## 14. Миграция и совместимость

1. **Перенос существующих норм из кода в данные** (этап реализации, не выполняется здесь):
   - **утверждённый перечень v1 (решение Q7-08а, по C-4):** обязательный перенос — **1.1 полосы петель шкафа** (`wardrobe-hinges.ts:30–39`) и **1.2 плотности фасадов** (`:17–21`); условия применимости переносимых норм — только в части «когда применять норму», в пределах перечня C-4;
   - **остальные категории остаются в своих слоях по C-4:** формулы и геометрия — в коде (Q7-08, §3.3); нормы, уже находящиеся в manifest-слое (`engine.sink.*`, `engine.supports.*`, `engine.lighting.*` и др.), в `ManagedRule` **не дублируются**; лимиты габаритов — по подтверждённому перечню; неиспользуемые (`minCountertopMeters`, readonly-дубли `wardrobe.*`, `widthWarning`) и неподтверждённые (`preliminary` — опоры/LED) **автоматически не переносятся**;
   - **дубль одного норматива в коде и управляемых данных не создаётся** — до переключения движка (§14.2) источником остаётся код, после — данные;
   - источник переноса — только подтверждённые значения; `source=owner_confirmed` для утверждённых, `preliminary` для неподтверждённых (опоры/LED);
   - импорт норм → draft → валидация → публикация (паттерн CA-T-208/R-14);
   - **паритет-тесты:** «данные ≡ текущие кодовые значения» для каждой переносимой нормы (как существующие тесты паритета `engine.sink.*` ↔ `SINK_RULES`);
2. **Переключение движка на чтение норм из inputs** — изменение кода контракта → **`calcVersion` (A6)**, golden-тесты, не может быть операцией админки. До переключения кодовые константы остаются источником, после — нормы в данных; двойное состояние в переходный период — риск §16.
3. **Старые проекты без `rulesSnapshotId` (решено Q7-02):** новый расчёт блокируется; чтение/отображение/история сохраняются; автоназначение актуального снимка и восстановление «по предположению» запрещены (§11.3); молчаливая подмена запрещена (design §5.4).
4. **strictObject/Zod и `schemaVersion` (решено Q7-07):** `StoredProject.rulesSnapshotId?: string` — **optional-метаданные-ссылка** той же категории, что существующие `calcVersion?`/`priceVersion?`/`pins?` (`types.ts:413–421`); **`schemaVersion` не повышается**, миграция не требуется; поля — только `optional` (design §5.6.3, OI-022/OI-027). В `ProjectPriceHistory` поле обязательно для новых записей и отсутствует в legacy-записях. **Автоматическое назначение снимка legacy-проектам запрещено**; отсутствие ссылки блокирует новый расчёт, но **не** историческое чтение (§11.3).
5. **Совместимость калькуляторов:** единый контракт, `scope` правил; кухонные и шкафные ветви получают нормы через один механизм.
6. **Обратная совместимость:** старые `CalculationRequest`/inputs без `rulesSnapshot` → нормализация явная (как legacy-нормализация `PriceRulesInput`, решение 6 ADR-06); до переключения движка — без изменений.

## 15. Тестирование (требования к будущей реализации)

1. **Паритет:** каждая перенесённая норма в данных идентична кодовой (golden + таблицы случаев кухня/шкаф).
2. **Fail-closed:** нет правила/тарифа/ссылки → ошибка; нулевой стоимости нет; wildcard-условие отклоняется.
3. **Воспроизводимость:** расчёт → публикация правил → пересчёт старого проекта применяет **закреплённый `rulesSnapshotId`** (§11.2); `ProjectPriceHistory` воспроизводит итог по набору идентификаторов (`schemaVersion`/`calcVersion`/`priceVersion`/`rulesSnapshotId`) — см. классификацию §11.4.
4. **Совместимость:** старые inputs без `rulesSnapshot`; старый проект без `rulesSnapshotId` — чтение разрешено, расчёт заблокирован (§11.3); strictObject-чтение.
5. **Паритет условий:** белый список условий исполняется идентично текущим проверкам `validation.ts` (класс 2 §3.2) — таблица соответствий «условие → правило».
6. **Инспектор:** каждый `CalculationLineId` объясняется правилом/формулой + тарифом + версиями (контракт §10.2).
7. **Импорт/публикация:** идемпотентность, отчёт, запрет авто-публикации, diff, подтверждения (паттерны CA-T-208/цены); ручное создание правил попадает только в `draft` (Q7-05).
8. **Кухня и шкаф:** все golden-сценарии (8) проходят без изменения результатов до переключения; после — только по утверждённому решению.
9. **Pinned:** публикация нового снимка правил не меняет результат расчёта существующего проекта (закрепление сохраняется); запись истории фиксирует собственный `rulesSnapshotId`.
10. **Legacy:** проект без `rulesSnapshotId` — конфигурация/история/сохранённый `PriceSnapshot` читаются, расчёт блокируется контролируемой ошибкой; автоназначение актуального снимка отсутствует.
11. **Исключение `preliminary`/`draft`:** такие записи не попадают в снимок и в `CalculationInputs`; обнаружение во входах → блокировка; отсутствие подтверждённого обязательного правила → ошибка, а не нулевая стоимость.

### 17.1. Технические вопросы, закрытые в ходе подготовки к утверждению

1. **Q7-09 (идентификатор) — закрыт.** `rulesSnapshotId` — непрозрачный сгенерированный ключ, формат не нормируется (§11.1 п.7). Точная схема данных `ManagedRule` утверждена через Q7-13 (§9); физическая схема/носитель — вне настоящего ADR (§5), определяются при реализации.
2. **Q7-10 (хранение) — утверждён.** Полная копия содержимого, неизменяемость, бессрочное хранение, запрет удаления при ссылках, валидация при публикации и разрешении (§11.1 п.8).
3. **Q7-11 (переход) — утверждён.** Контракт операции — §11.5; legacy-проекты в v1 остаются заблокированными, retro-процедура и автоназначение не вводятся.
4. **Q7-08а (перечень переноса) — утверждён.** Обязательный перенос 1.1+1.2, условия — в части применения норм, остальные категории — по C-4, без дублей (§14.1).
5. **Пакетный пересчёт — закрыт технически:** при публикации правил не выполняется и в scope не входит (решение Q7-11, §12 п.8).

**Остаётся уровнем реализации (не блокирует утверждение архитектуры):** точные строки кодов ошибок §10.4, помеченные **[ПРЕДЛОЖЕНИЕ]** (имена классов — при реализации контракта; существующие `DataResolverErrorCode` не расширяются настоящим ADR); физическая схема хранения снимков (§5).

**Не закрытыми остаются** (не относятся к настоящему ADR, вне scope): Q-01…Q-14 ТЗ; CA-RISK-002 (политика `calcVersion`); исторические сборки (ADR-03/CA-T-412); CA-T-602/603 deployment (блокеры Q6); Q-A17-2.4; U-3/U-4/U-5, D-5/D-6 (ожидают решения по калькуляторам). Эти вопросы не препятствуют утверждению ADR-07: CA-T-602/603 ограничивают только production-публикацию (§13), остальные не относятся к слою управляемых правил.
