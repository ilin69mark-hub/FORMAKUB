# ADR-01: Хранилище данных Calculation Admin — SQLite

- **Статус:** утверждён владельцем 2026-11-07
- **Задача:** CA-T-101 (`CALCULATION_ADMIN_IMPLEMENTATION_PLAN.md`, Фаза 1); основание — прямое решение владельца (пакет «CA-T-101 / CA-T-102», Q1/OI-049)
- **Затрагивает:** дизайн §12, §13, §16.1 (реестр ADR), §16.2 (варианты хранения); ТЗ T-0.1, T-2.4, T-3.4
- **Вопрос ADR (дизайн §16.1):** носитель данных Calculation Admin: JSON-файлы (как сегодня) vs SQLite vs Postgres; судьба `data/*.json`; том/backup

## Статус сверки (2026-11-10; уточнение владельца 2026-11-10)

- **Архитектурный статус:** **ACCEPTED** (утверждён владельцем 2026-11-07; уточнён 2026-11-10).
- **Статус реализации:** **PARTIAL** (по указанию владельца; архитектурная модель принята, остаточные ограничения не объявлены закрытыми).
- **Подтверждено:** SQLite Storage Adapter; одна БД в постоянном Docker volume; контролируемая JSON→SQLite миграция; ACID-транзакции записи; single-instance; JSON не используется как параллельное постоянное хранилище.
- **Решение владельца 2026-11-10:** сохранить текущую модель **SQLite + JSON-payload** (`collection_state`); целостность обеспечивать **на уровне приложения**; нормативное требование реляционных FK/`UNIQUE`/`NOT NULL` пересмотрено и не применяется к текущей модели; миграция схемы **не выполняется**.
- **Остаётся PARTIAL:** Q13 retention, Q14 архив и остаточные ограничения app-level целостности не закрыты; schema migration не планируется.
- **Связанные задачи:** CA-T-101/103/110 — DONE; CA-T-608 — DONE. Отдельной задачи на реляционные ограничения нет.

## Контекст

**[ФАКТ]** Сегодня данные хранятся в JSON-файлах `data/*.json` через `src/lib/server/store.ts` (in-process `Map`-локи, одна запись = один файл, ограничения §13.1 дизайн-документа); ни БД, ни ORM в репозитории нет. Предварительная рекомендация дизайн §16.2 — «JSON предпочтителен для v1» — носила характер варианта до утверждения настоящего ADR.

## Решение (утверждено владельцем)

1. **SQLite** — единственное основное хранилище данных Calculation Admin.
2. **Одна база данных — один файл.**
3. Файл базы размещается в **постоянном Docker volume**.
4. Применяются **ACID-транзакции**. Целостность данных обеспечивается **на уровне приложения**; реляционные FK/`UNIQUE`/`NOT NULL` не являются нормативным требованием для текущей JSON-payload модели `collection_state`. **Уточнение владельца 2026-11-10;** миграция схемы не выполняется.
5. **Архитектура одного экземпляра приложения сохраняется** (Q2/R-03: один инстанс, in-process блокировки).
6. **JSON-файлы не используются как параллельное постоянное хранилище** (настоящее решение отменяет предварительную рекомендацию дизайн §16.2 «JSON для v1»).
7. **Миграция существующих данных (`data/*.json`) должна быть контролируемой, без потери данных** — отдельной задачей с проверкой читаемости/сверкой после переноса.

## Последствия

- Требуется контролируемая миграция JSON → SQLite (перенос проектов, справочников, прайсов, журналов) с подтверждением отсутствия потерь; до завершения миграции прежние файлы не удаляются и не поддерживаются как второе хранилище.
- Атомарность многополевых операций обеспечивается транзакцией СУБД вместо in-process локов; существующий код `store.ts` меняется через адаптер (CA-T-103) без изменения поведения потребителей.
- Требование «один экземпляр» сохраняется; масштабирование на несколько инстансов не входит в объём решения.

## Не решается настоящим ADR

- Физическая модель архива при вытеснении (Q14/R-02 — связано с ADR-01, но в утверждённый состав не входит);
- retention истории (Q13);
- инфраструктурная реализация volume/backup — ADR-03;
- конкретный механизм и порядок миграции — реализация (отдельная задача, не входит в CA-T-101).
