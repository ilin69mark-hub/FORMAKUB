## A. Executive Summary

Проверено **22 задачи/вопроса**: 14 — `ALREADY IMPLEMENTED`, 1 — `READY WITH CONDITIONS`, 2 — `BLOCKED`, 5 — `NEEDS OWNER DECISION`.

**Общая оценка:** инфраструктурный слой Managed Assembly Rules (контракт, хранение, валидация, публикация снимка, разрешение в DataResolver, переход проекта) реализован и покрыт тестами. Однако **сквозной сценарий «правило → публикация → расчёт» не работает**:

1. **ADR-07 остаётся DRAFT** и прямо запрещает реализацию до APPROVED (`ADR-07:4,18`; `CONFIRMED`), при этом Slice 1–3 уже реализованы — формальное противоречие, требующее решения владельца.
2. **Нет операции перевода правила draft → published** (`managed-rules.ts:618–623` только фильтрует уже опубликованные правила; `CONFIRMED`). Публикация снимка через сервисы невозможна: тесты обходят это прямой записью файла.
3. **Движок не потребляет `rulesSnapshot`** — пятая группа передаётся, но `engine.ts` её не читает; полосы петель и плотности фасадов остаются в коде (`wardrobe-hinges.ts:17,30`; `CONFIRMED`). Утверждённый Q7-08а перенос 1.1/1.2 **не выполнен** (0 норм перенесено).
4. **Production-данные не содержат снимка правил** → create/preview и публичный калькулятор немедленно fail-closed (`CONFIRMED` по `data/formakub.db` и коду DataResolver).
5. **CA-T-613** (HTTP/UI) не имеет спецификации маршрутов/UI и не может включать публикацию до закрытия deployment-предусловий (CA-T-511).

**Вывод:** к планированию можно переходить **условно** — после решения владельца об утверждении ADR-07 и семантике публикации правил. Планировать без этих решений нельзя: дальнейшая реализация формально запрещена ADR-07, а CA-T-613 без lifecycle публикации воспроизведёт тупик.

## C. Архитектурные и технические нюансы

1. **ADR-07 DRAFT vs реализация (`CONFIRMED`).** `ADR-07:4,18` запрещает реализацию до APPROVED; Slice 1–3 реализованы. Требуется формальное утверждение (D-1). Шесть решений остаются «предварительными» (`ADR-07:24–31`), хотя код на них опирается.
2. **Нет жизненного цикла публикации правила (`CONFIRMED`).** Публикация снимка возможна только при наличии `status=published` правил, но перевода draft→published нет. Сквозной сценарий нерабочий; тесты используют прямую запись в файл.
3. **Движок не потребляет правила (`CONFIRMED`).** `engine.ts` не читает `inputs.rulesSnapshot`; нормы 1.1/1.2 остаются константами. Передача пятой группы — контрактная, без влияния на цену.
4. **Production fail-closed (`CONFIRMED`).** В `data/formakub.db` нет `rules-snapshots.json`; create/preview и публичный `/api/calculation-inputs` вернут `RULES_SNAPSHOT_MISSING`. Это соответствует утверждённой семантике Q7-02/Q7-11, но является блокером развёртывания.
5. **Storage Adapter (`CONFIRMED`).** Атомарность — только в пределах коллекции. CA-T-612 использует порядок «аудит → проект»; обратный сбой (аудит есть, проект не изменён) возможен и документирован. Межколлекционная транзакция — отдельное решение (N3).
6. **Idempotency replay (`CONFIRMED`).** Повтор `operationId` возвращает текущий проект, а не снимок состояния исходной операции; после последующего перехода replay вернёт другой pin. Не покрыто тестом; не исправлялось.
7. **`expectedVersion = updatedAt` (`CONFIRMED`).** У `StoredProject` нет revision-поля; optimistic locking опирается на `updatedAt` (существующая метка). Риск коллизии смягчён `nextUpdatedAt` (+1 мс), но семантика слабее счётчика.
8. **Опубликованное правило изменяемо in-place (`CONFIRMED`).** `updateManagedRule` инкрементирует `version` и сохраняет статус; отдельной неизменяемой редакции нет. Старые снимки защищены копированием, но «опубликованная редакция» как сущность отсутствует — расхождение с ADR §11.1 п.4 требует уточнения (N5).
9. **Повреждение одного снимка блокирует всё (`CONFIRMED`).** `resolveActiveRulesSnapshot` валидирует все записи коллекции; один повреждённый снимок → `RULES_SNAPSHOT_CORRUPT` для всех новых расчётов. Fail-closed корректен, но операционно жёстко; политика восстановления не определена.
10. **RBAC (`CONFIRMED`).** Сервисы правил/перехода не проверяют permissions; маршрутов нет, поэтому уязвимости в runtime пока нет. При CA-T-613 обязательны `catalog.write`/`price.publish`/`recalc.run` (Q7-04), `AdminAuditLog` и подтверждения (CA-T-604/606).
11. **Аудит (`CONFIRMED`).** `AUDIT_ACTIONS` выводится из `auditActionSchema.options` (`audit-ui.ts:17`), новые действия `rule.*` и `project.rules_transition` доступны фильтрам автоматически — доработка UI не требуется.
12. **Тестовые пробелы (`CONFIRMED`):** нет теста закрепления снимка в `saveProject`; нет теста replay после последующего перехода; нет теста конкурентных переходов; нет тестов движка на потребление правил (функция отсутствует); нет тестов инспектора/диагностики (функции отсутствуют).
13. **Документационные расхождения (`CONFIRMED`):**
    - `PROJECT_BACKLOG.md` Block 10: «25 тестов» для CA-T-610 — фактически 24;
    - `CALCULATION_ADMIN_IMPLEMENTATION_PLAN.md` не содержит CA-T-610…613 в реестре задач (только changelog v0.99/v1.00) — нумерация новых задач не заведена формально;
    - ранее известное: ADR-06 содержит устаревшее утверждение об отсутствии `priceVersion` (код содержит поле).
14. **Совместимость (`CONFIRMED`).** Поле `rulesSnapshotId` optional, `SUPPORTED_SCHEMA_VERSION = 2` не повышен, миграций нет; старые проекты читаются; `recalculateProject` сохраняет поле через `...stored` (`projects.ts:540+`). Legacy-проекты без привязки блокируются для расчёта — по решению Q7-11.
15. **Эксплуатация.** `CA-T-511` и S3/Keycloak provisioning — внешние; production-публикация и включение publish-маршрутов должны ждать их (Q6).

## D. Решения владельца

### D-1. Утвердить ADR-07 (и подтвердить шесть предварительных решений)

- **Последствия:** (а) легализует уже реализованное и разблокирует планирование; (б) требует правок ADR; (в) формально запрещает дальнейшую реализацию (текущее состояние противоречиво).
- **Рекомендация:** (а) — семь решений утверждены, шесть предварительных зафиксированы, блокирующих вопросов нет (`ADR-07:595–598`).
- **Зависимые задачи:** все N1–N5, CA-T-613.

### D-2. Семантика публикации правил (N5)
- **Варианты:** (а) публикация снимка публикует выбранные draft-правила (одна операция); (б) отдельная `publishRule` перед снимком; (в) снимок публикует все draft автоматически.
- **Последствия:** (а) — минимум операций, но требует явного выбора набора; (б) — больше шагов, зато прозрачный аудит; (в) — противоречит «draft не участвует» и ручному контролю.
- **Рекомендация:** (а) с явным списком draft-правил и подтверждением; иначе (б).
- **Зависимые:** N1, CA-T-613, N4.

### D-3. Перенос норм 1.1/1.2 и изменение расчёта
- **Варианты:** (а) перенести значения как `owner_confirmed`, переключить движок, bump `calcVersion`, обновить golden; (б) отложить перенос; (в) перенести без переключения движка.
- **Последствия:** (а) меняет производственный расчёт (требует релиза и проверки паритета); (б) Q7-08а остаётся невыполненным; (в) создаёт дубль слоёв без эффекта.
- **Рекомендация:** (а) с паритет-тестами и релизной процедурой; владелец подтверждает значения полос/плотностей.
- **Зависимые:** N1, N2, N4.

### D-4. Атомарность «проект + аудит» (N3)
- **Варианты:** (а) принять документированное ограничение; (б) добавить транзакционный API Storage Adapter (SQLite — реальная транзакция; JSON — запрет/имитация).
- **Последствия:** (а) редкий сбой оставляет аудит без изменения; (б) инфраструктурная работа и изменения адаптера/тестов.
- **Рекомендация:** (а) для текущего single-instance контура; (б) — только если аудит признан юридически критичным.
- **Зависимые:** CA-T-612 (уже реализован), возможные будущие операции.

### D-5. Scope инспектора/диагностики (N2)
- **Варианты:** (а) включить в следующий этап; (б) отложить; (в) ограничиться диагностикой «проекты без снимка».
- **Рекомендация:** (в) как минимум, (а) — после N1.
- **Зависимые:** N2, CA-T-613 (отображение версии).

### D-6. Разрешение publish-маршрутов до CA-T-511
- **Варианты:** (а) только read/draft-маршруты, публикация выключена; (б) включить публикацию после CA-T-511; (в) включить раньше.
- **Последствия:** (в) противоречит Q6/ADR-07 §13 (production-публикация не безопасна).
- **Рекомендация:** (а) сейчас, (б) — после закрытия CA-T-511.
- **Зависимые:** CA-T-613, N4.

## G. Итоговая готовность

- **Переходить к планированию:** **можно условно** — после D-1 и D-2; без них дальнейшая реализация формально запрещена (ADR-07 DRAFT) и не имеет рабочего сквозного сценария.
- **Что решить до планирования:** утверждение ADR-07 (+6 предварительных решений), семантика публикации правил, подтверждение значений норм и релизного изменения расчёта, scope инспектора, режим атомарности, порядок включения publish-маршрутов.
- **Готовы к немедленному планированию без решений:** CA-T-613 в части read/draft (после уточнения scope), N3 (если выбран вариант «б»).
- **Требуют отдельной работы:** CA-T-511 (внешний provisioning), N4 (seed/runbook), N1 (расчётный релиз).
- **Нельзя считать готовым:** сквозной сценарий Managed Rules — инфраструктура есть, публикация правил и потребление движком отсутствуют; production-данные не содержат снимка.
